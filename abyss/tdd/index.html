01 · Overview

A 10–15 minute playable tech demo. The player is a xenobiologist studying the wildlife of a small underwater cove. There are no weapons: progression comes from understanding creatures. Each research entry needs a scan, then the observation of specific behaviours. Completed entries open deeper zones, down to a final encounter with an immense presence glimpsed in the dark.

Pillars, and how the tech serves them

Curiosity“I want to get closer.”
Believable 3D steering, readable idle behaviours, a creature that comes to the player.
Tension“It warns before acting.”
Progressive vigilance with explicit stages and telegraphed charge timings, all in data.
Readability“I always understand.”
Every observable behaviour emits a signal (posture, light, sound) driven by data, plus debug tools to check it.
◎Portfolio goals
  1. Show believable, readable and pleasant-to-watch creature AI.
  2. Show that these systems are tunable by Designers without code, with the Creature Tuner.
  3. Show that I work inside Unreal’s frameworks (AI Perception, Behavior Trees, State Tree, EQS, Gameplay Tags, Editor Utility Widgets) instead of reinventing them.
⚠Constraints
  • Blueprint first. C++ only if a measured performance problem requires it, always proposed and justified first.
  • Mid-range machine, 1K textures max. Target: 60 fps at 1080p, AI budget ≤ 2 ms on the game thread.
  • Git without LFS, small incremental pushes. Everything in English.
  • Art: primitives and free Fab assets only. No modelling, no complex materials.

Scope tiers

  1. Minimum viableMust ship

    Player swimming, 3D navigation, fish shoal, sea serpent predator, observation mechanic and research journal, Creature Tuner, video.

  2. Target

    Curious creature, full encyclopedia, zone-based spawning with EQS, final abyss zone with the Abyssal Presence, behaviour nudges.

  3. Bonus

    Day/night cycle influencing behaviours.

  4. Version 2

    A small pilotable submersible, after release.

02 · Architecture

⚙Principles
  • Components over inheritance for behaviours, small inheritance trees for actors.
  • Event Dispatchers to communicate, interfaces when several components may react, direct calls when the target is unique.
  • Pull + push: getters at init or decision time, dispatchers for changes.
  • Data: one Primary Data Asset per species, one Data Table row per research task, Toolkit variables for global tuning.
  • Data Assets are read-only at runtime. In play-in-editor they are shared with the editor, so writing to one from gameplay would change it for good. Only the Creature Tuner writes to them, on purpose.
  • Defensive Blueprints: every reference validated, a clear script error on critical failures, every Switch has a handled Default.

Why a Behavior Tree here and a State Tree there

Behavior TreeState Tree
ModelPriority tree, re-evaluated continuouslyHierarchical state machine with explicit transitions
StrengthsReactive (decorators, observer aborts), mature tooling, Gameplay Debugger supportThe current state is explicit and readable; runs on any Actor through a component, without an AI Controller
WeaknessesStates are implicit; the Blackboard is rigidYounger system, API still evolving between engine versions
→Decision
Sea serpent
Behavior Tree. A reactive, priority-driven brain: being deterred must interrupt a charge. Observer aborts express this directly.
Shoal
State Tree. A group with a few clear states (Cruise, Flee, Regroup), and a single actor that is not a pawn. A State Tree component fits it without a fake AI Controller.
Rule
One brain per creature. Mixing both on the same creature would make “who decides?” ambiguous and harder to debug.

≡One pipeline for scans and observations

A scan is simply a research task whose observable is permanent (active while the creature is alive). Scans and behaviour observations share one pipeline: there is no separate scan system.

Each task row holds its observable tag, required duration, max range and angle, prerequisites, the zone it unlocks, and hints that get more precise over time.

04 · Creature AI

3D navigation without NavMesh, in three layers

Unreal’s NavMesh only covers walkable surfaces, so creatures navigate in three layers, following Reynolds’ model (action selection, then path selection, then locomotion). It continues my Flying AI project.

⌖Layer 2: EQS routeCheap tests first
  1. Distance to the creature: a filter, kept as a ring between a min and a max distance.
  2. Trace from the creature: a filter, with a sphere as wide as the creature plus a margin.
  3. Distance to the goal: a score, closer is better.
  4. Dot with the current velocity: a score that rewards continuity, for smooth curves.

The distance filter runs first, so fewer points need a trace. All values come from the species data.

≋Layer 3: locomotion, every tick
desired  = direction to current waypoint
smoothed = interp at Turn Rate      ← no instant turns
speed    = lower in tight curves
rotation = face velocity, roll from turn rate
safety   = short sphere trace: hit → re-query now
progress ≥ 60 % of segment → next waypoint
           (chains without stopping)
depth band: goals between floor and surface
no progress for a while → OnStuck

Perception

AI Perception (Sight and Hearing) is set to generous maximum values, and each species’ perception is filtered in Blueprint from its data. Why: sense settings can’t be changed at runtime from Blueprint, but the Creature Tuner must change perception live. The player’s sprint is a noise event; the flash is sent directly through an interface, since light is not a perception sense.

✦Fish shoalState Tree

One actor, 30 fish as instances of one mesh, without collision. The actor is the anchor: it wanders with the steering component, and the fish follow it with boids rules (cohesion, alignment, separation, anchor pull), updated at 30 Hz in one batch per frame.

Cruisethreat closeFleecalm againRegroupback togetherCruise

The fish flash silver when they flee, with a “whoosh”. The tutorial: sprint into the shoal, then observe the flight.

∿Sea serpentBehavior Tree

A body made of segments that follow the head’s trail. The body passes exactly where the head passed, so it never cuts corners through rocks the head avoided. Only the head collides.

CalmSuspiciousWarningAggressive

Vigilance rises while the player is in its territory (faster when closer) and with sprint noise, then decays. A flash deters it.

A charge that hits pushes the player back, shakes the camera and locks input for 1 s. No death: the punishment is losing position and time, which keeps the demo patient-friendly. Three ways to deter it, without a weapon: flash it, stay out of its territory, or sprint away. A Warning always comes before a Charge.

+One system, two scalesTarget tier
Abyssal Presence
Not a real AI: a scripted pass along a spline, in the dark beyond the flashlight, lit only by a few bioluminescent lights. It reuses the serpent’s segment chain at giant scale. Showing that one system serves both a 6 m serpent and a 150 m leviathan is a deliberate point.
Readable signals
A signals component maps each observable to a light (colour, intensity, pulse) and a sound, from the species data. A Designer can change how a behaviour announces itself from the Creature Tuner, without code.

05 · Observation system

?Why a registry

The tracker only goes through events that are active right now (usually 1 to 5), instead of searching every actor every 0.1 s, or using an overlap that ignores what is actually observable. Emitters push, the tracker pulls a short list. It lives on the Game State because subsystems would need C++.

♥Forgiving by design

If the target is lost, a 0.5 s grace time, then progress decays slowly: never an instant reset. Tutorial values are generous (25° angle, 2 s).

07 · Creature Tuner

A Designer picks a species, tunes it, spawns it and watches its perception, vigilance and observable events live, without code. It is the centrepiece of the demo video.

⚒FeaturesEditor Utility Widget
  • Species picker from the Asset Registry, child classes included.
  • Edit values in a Details View bound to the Data Asset: a new field added to the species class shows up on its own.
  • New species by duplicating an existing one, then changing mesh and values.
  • Spawn in play in front of the camera, and apply live to every creature of that species.
  • Live monitor: the selected creature’s behaviour, vigilance, perceived actors and speed, about 5 times per second.
  • Debug layers: perception cone, vigilance bar, trajectory, EQS waypoints, safety trace, goal, active observables.
⇄Editor ↔ play session

The widget lives in the editor world, the creatures in the play world. Assets are shared by both, so a Data Asset serves as the channel:

Creature Tunereditor world DA_TunerChanneltransient bridge reference Bridge actorplay world · non-shipping

The bridge registers itself in the channel when play starts and clears it when play ends. The reference is never saved: if it’s empty, the widget shows “Start PIE to spawn”. The same sharing explains live tuning: the creature in play reads the very asset the Details View edits.

▶Video scenarioTarget
Zero code
A Designer duplicates the curious creature, renames it Glimmer Ray, swaps the mesh, makes it shyer (fear rises faster, larger inspect distance) and gives its inspect signal a yellow light. They spawn it in play and watch its fear bar and signals react to the player.

08 · Debug tools & risks

On demand, each creature draws its perception cone (species values), vigilance bar and stage, trajectory, current and next EQS waypoints, safety trace (green if free, red if hit), goal and active observables. The Gameplay Debugger covers Behavior Trees, perception and EQS; the Visual Logger replays a charge after the fact. Debug drawing is off in shipping builds.
