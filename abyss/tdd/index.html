01 · Overview

Key pointA 10–15 min demo with no weapons: you progress by understanding creatures, scanning them and observing their behaviours. The scope is tiered so a playable demo always ships.

Curiosity“I want to get closer.”
Believable 3D steering, readable idle behaviours, a creature that comes to the player.
Tension“It warns before acting.”
Progressive vigilance with explicit stages and telegraphed charge timings, all in data.
Readability“I always understand.”
Every observable behaviour emits a signal (posture, light, sound) driven by data, plus debug tools to check it.
  1. Minimum viable Must ship

    Swimming, 3D navigation, shoal, sea serpent, observation and journal, Creature Tuner, video.

  2. Target

    Curious creature, encyclopedia, EQS spawning, final abyss zone, behaviour nudges.

  3. Bonus

    Day/night cycle influencing behaviours.

  4. Version 2

    A small pilotable submersible, after release.

  • Blueprint first
  • C++ only if measured
  • 60 fps · 1080p
  • AI ≤ 2 ms / frame
  • Git, no LFS
  • Primitives + free Fab assets
Portfolio goals and constraints in full
  1. Show believable, readable and pleasant-to-watch creature AI.
  2. Show that these systems are tunable by Designers without code, with the Creature Tuner.
  3. Show that I work inside Unreal’s frameworks (AI Perception, Behavior Trees, State Tree, EQS, Gameplay Tags, Editor Utility Widgets) instead of reinventing them.
  • Blueprint first. C++ only if a measured performance problem requires it, always proposed and justified first.
  • Mid-range machine, 1K textures max. Target: 60 fps at 1080p, AI budget ≤ 2 ms on the game thread.
  • Git without LFS, small incremental pushes. Everything in English.
  • Art: primitives and free Fab assets only. No modelling, no complex materials.

02 · Architecture

Key pointComponents over inheritance. A creature is a light pawn plus small components (steering, vigilance, signals, debug). Brains set goals, components act, and one brain per creature.

Behavior TreeSea serpent

Reactive and priority-driven: being deterred must interrupt a charge. Observer aborts express this directly.

vs
State TreeFish shoal

A few clear states (Cruise, Flee, Regroup) on one actor that isn’t a pawn: no fake AI Controller needed.

All principles, and the full BT vs State Tree comparison
  • Event Dispatchers to communicate, interfaces when several components may react, direct calls when the target is unique.
  • Read when deciding, announce changes: values are read when a creature starts or makes a decision; changes are announced through Event Dispatchers.
  • Data: one Primary Data Asset per species, one Data Table row per research task, Toolkit variables for global tuning.
  • Data Assets are read-only at runtime. In play-in-editor they are shared with the editor, so writing to one from gameplay would change it for good. Only the Creature Tuner writes to them, on purpose.
  • Defensive Blueprints: every reference validated, a clear script error on critical failures, every Switch has a handled Default.
Behavior TreeState Tree
ModelPriority tree, re-evaluated continuouslyHierarchical state machine with explicit transitions
StrengthsReactive (decorators, observer aborts), mature tooling, Gameplay Debugger supportThe current state is explicit and readable; runs on any Actor through a component, without an AI Controller
WeaknessesStates are implicit; the Blackboard is rigidYounger system, API still evolving between engine versions

One brain per creature: mixing both on the same creature would make “who decides?” ambiguous and harder to debug.

04 · Creature AI

Key pointUnreal’s NavMesh only covers walkable ground, so creatures navigate in three layers (Reynolds’ model). It continues my Flying AI.

Perception trick. Sense settings can’t change at runtime from Blueprint, but the Tuner must change perception live. So the engine perceives wide, and each species filters in Blueprint from its data.

One system, two scales. The final Abyssal Presence is a scripted pass reusing the serpent’s segment chain at giant scale: a 6 m serpent and a 150 m leviathan, one system.

EQS tests, steering loop and the serpent’s Behavior Tree

EQS route, cheap tests first: distance to the creature (a filter, kept as a ring), sphere trace from the creature (a filter), distance to the goal (score, closer is better), dot with the current velocity (score that rewards continuity, for smooth curves). The distance filter runs first, so fewer points need a trace.

No death: a charge pushes the player back, shakes the camera and locks input for 1 s. Three ways to deter it, without a weapon: flash it, stay out of its territory, or sprint away.

05 · Observation system

Key pointWhen a creature starts a behaviour worth observing, it adds it to a shared list, and removes it when it stops. While the player scans, the game only checks that short list every 0.1 s, never every actor in the level.

Forgiving by design. Lose the target and you get a 0.5 s grace time, then progress decays slowly: never an instant reset.

06 · Player patience

Key pointWatching creatures can get slow, so pacing has targets, checked in playtests. When a task stalls, the creatures perform that behaviour more often.

  • < 1 minto the first successful observation
  • < 3 minper next task, for an attentive player
  • 10–15 minfor the full demo, 8 tasks

07 · Creature Tuner

Key pointThe Creature Tuner is an Editor Utility Widget: a Designer picks a species, tunes it, spawns it and watches it react live, without code. The editor and the play session are two worlds, so a Data Asset is the bridge.

Video scenario. Duplicate the curious creature, rename it Glimmer Ray, make it shyer, give its signal a yellow light, spawn it: zero code.

How the bridge works

The bridge registers itself in the channel when play starts and clears it when play ends. The reference is never saved: if it’s empty, the widget shows “Start PIE to spawn”. The same sharing explains live tuning: the creature in play reads the very asset the Details View edits. A new field added to the species class shows up in the tool on its own.

08 · Risks & debug

Key pointEvery major risk has a fallback written before it happens. The three that matter most:

Performance30 boids in Blueprint

≈ 435 neighbour pairs per update.

Plan B30 Hz update, a third of the fish per frame, profiling. The only valid case for C++, if measured over budget.

CentrepieceEditor ↔ play communication

Could block the Creature Tuner.

Plan BAn early spike. Fallback: tune in the editor, spawn with a debug key.

New systemState Tree learning curve

Its API still changes between versions.

Plan BShoal kept to 3 states, timeboxed. Fallback: an Enum state machine, same logic.

Debug tools: on demand, each creature draws its perception cone (species values), vigilance bar and stage, trajectory, EQS waypoints, safety trace (green if free, red if hit), goal and active observables. The Gameplay Debugger covers Behavior Trees, perception and EQS; the Visual Logger replays a charge after the fact. Debug drawing is off in shipping builds.
